# Documentation d'Implémentation Flexify (H2H, SEPA & Reporting)

Ce guide centralise toutes les informations techniques nécessaires pour une intégration complète de l'API Flexify.

## 1. Informations de Base et Endpoints
Flexify utilise une architecture **REST** via **HTTPS** uniquement. Les réponses sont au format **JSON**.

### URLs des Services
| Type de Service | URL Endpoint |
| :--- | :--- |
| **Host to Host (H2H)** | `https://h2h.flexify.finance` |
| **Hosted Payment Page (HPP)** | `https://hpp.flexify.finance` |
| **Merchant Portal** | `https://my.flexify.finance` |
| **Reporting API (Merchant)** | `https://api.flexify.finance` |
| **Reporting API (Admin)** | `https://admin-flexify.finance` |

## 2. Configuration et Sécurité
*   **Whitelisting IP :** Votre adresse IP serveur **doit** être autorisée par Flexify avant toute requête H2H ou HPP.
*   **Identifiants :** Les clés API (`apiKey` et `apiSecret`) se récupèrent dans la section "Projects" du portail marchand.
*   **Mode Test :** Déterminé par la clé API utilisée ; aucune requête réelle n'est envoyée aux institutions financières en mode test.
*   **Conformité PCI :** Obligatoire pour les transactions par carte en intégration H2H.

## 3. Authentification HMAC-SHA256 (H2H Gate API)
Chaque requête doit être signée. Une absence de signature entraîne un rejet automatique.

### Étape 1 : Génération du Digest (Pour POST)
Calculez le hash SHA-256 du corps de la requête (JSON), puis encodez-le en Base64.
Format : `Digest: SHA-256=[hash_base64]`.

### Étape 2 : Construction du Payload de Signature
*   **Requête POST :** `host: [host]digest: [digest]content-length: [length]date: [date]`.
*   **Requête GET :** `host: [host]date: [date]`.

### Étape 3 : Création de l'en-tête Authorization
Signez le payload avec votre `apiSecret` via HMAC-SHA256, encodez en Base64, puis assemblez l'en-tête :
`Signature keyId="[apiKey]", algorithm="HmacSHA256", headers="host digest content-length date", signature="[signature]"`.

## 4. Endpoints de Transaction (V1)

### Créer un Paiement (SEPA ou Carte)
*   **Endpoint :** `POST /v1/payment`.
*   **Champs clés :** `method` (ex: "sepa" ou "card"), `mode` ("initial"), `reference` (unique), `currency` (ex: "EUR"), `amount`, `customer` (identifier, email, country, ip, etc.).
*   **Callbacks :** Fournissez une `callback_url` pour recevoir les notifications de statut.

### Effectuer un Payout (Virement sortant)
*   **Endpoint :** `POST /v1/payout`.
*   **Processus :** Préparation, signature, envoi, puis attente du callback ou vérification manuelle.

### Effectuer un Refund (Remboursement)
*   **Endpoint :** `POST /v1/refund`.
*   **Conditions :** Uniquement pour les transactions parentes "success" et dans un délai de 180 jours.

### Tokenisation de Carte (Optionnel)
*   **Endpoint :** `POST /v1/card/tokenize`.
*   Permet de créer des tokens réutilisables pour des paiements futurs sans stocker les données sensibles.

## 5. Gestion des Statuts et Callbacks

### Liste des Statuts de Transaction
| Statut | Final | Description |
| :--- | :--- | :--- |
| `new` | Non | Créé. |
| `pending` | Non | En attente de traitement ou de callback. |
| `success` | Oui | Succès. |
| `declined` / `failed` | Oui | Refusé/Échec. |
| `expired` | Oui | Expiré (20 min pour l'intention, 7 jours pour le paiement). |

### Validation Obligatoire du Callback
Flexify envoie un POST sur votre `callback_url`. **Vous devez valider la signature** pour éviter toute usurpation :
1.  Vérifiez que le `digest` correspond au corps reçu.
2.  Vérifiez que le `keyId` est le vôtre.
3.  Recalculez la signature à partir des en-têtes listés dans le paramètre `headers` de la signature reçue.
4.  Répondez par un code **HTTP 200** sous 30 secondes.

**Stratégie de Retry :** Si votre serveur ne répond pas 200, Flexify réessaie jusqu'à 15 fois sur une période croissante (de 5s à 1h).

## 6. Balance et Reporting

### Vérifier le Solde du Projet
*   **Endpoint :** `GET /v1/balance`.
*   **Réponse :** Retourne le `current_balance`, `available_balance` et les détails d'overdraft par devise.

### API de Reporting (Transactions)
*   **Endpoint :** `GET /v1/report/transaction`.
*   **Authentification :** **Basic Auth** (Username = API Key, Password = Secret Key).
*   **Paramètres requis :** `merchant_identifier` (ex: MR_TEST) et une plage de dates (`created_at_from/to` ou `updated_at_from/to`).

## 7. Référentiel des Codes d'Erreur (Extraits)
*   **0 :** Succès.
*   **11 :** Signature invalide ou Secret API incorrect.
*   **30/31 :** Paramètres invalides ou manquants.
*   **500 :** Fonds insuffisants sur le compte du projet.
*   **1020 :** Fonds insuffisants sur le compte/carte du client.
*   **1021/1022 :** Montant ou devise non supportés.
*   **1054 :** Méthode de paiement (ex: SEPA) non configurée pour ce compte.

***

**Conseil pour SEPA :** Assurez-vous que l'objet `sepa` dans les réponses de rapport est bien traité pour récupérer les détails IBAN si nécessaire.
