# Whitepay API Integration Rules (Next.js - Deep Spec)

## 0. Flux global (ordre obligatoire)
- **Avant tout payout** : le compte merchant Whitepay doit être alimenté via le **Crypto Top-Up**.
  1. Créer une invoice top-up via la **WhitePay Crypto Top-Up API** → cela crédite le compte merchant.
  2. Écouter le webhook **Final Amount Received** (`transaction_received_total`, `received_currency`) sur la **même URL** que les withdrawals.
  3. Une fois le solde crédité, les payouts vers les utilisateurs fonctionnent (sinon erreur type "balance = 0").
- **Une seule URL de webhook** pour deposits (top-up) et withdrawals : ex. `https://votredomaine.com/api/whitepay/webhook`. Whitepay envoie les deux types d’événements sur cette URL.

## 1. Endpoints & Logic
- **Base URL**: `https://docs.whitepay.com`
- **Standard Flow**: `POST /private-api/convert-withdrawal` -> Reçoit un `transactionID`.
  - **Délai de confirmation**: L'exécution doit être confirmée via `POST /confirm` dans les **30 secondes** [1-4].
  - **Expiration**: Si > 30s, appeler `POST /refresh` pour obtenir un nouveau taux avant de confirmer [5-8].
- **Instant Flow**: `POST /private-api/convert-withdrawal/instant` (Combine création, taux et confirmation) [9-12].

## 2. Types de Données (Strict)
### Statuts de Transaction
- `WAITING_CONFIRMATION`: Créé, en attente de confirmation [13-16].
- `PENDING_WITHDRAWAL`: Confirmé, conversion en cours [13-16].
- `PROCESSING_WITHDRAWAL`: Envoyé sur la blockchain [13-16].
- `COMPLETE` & `DECLINED`: États finaux [17-20].

### Travel Rule (Obligatoire pour l'EEE)
Si l'utilisateur est dans l'Espace Économique Européen (EEE), l'objet `travelRule` doit inclure :
- `type`: "individual" ou "entity" [21-24].
- `vasp`: Nom de la plateforme de destination [5-8].
- `name`: Nom de l'individu ou de l'entité [5-8].
- `address`: Adresse physique du destinataire [5-8].

## 3. Schéma des Réponses (Payloads)
L'IA doit typer les réponses selon ce format :
- L'objet racine contient souvent une clé `transaction` [25-28].
- Champs clés : `id`, `exchange_rate`, `estimated_at`, `target_value`, `fee`, et les objets `currency` / `target_currency` avec leur `ticker` et `precision` [29-40].

## 4. Instructions de génération de code
- Toujours vérifier si un `memo` est requis pour le `network` choisi (ex: TON, STELLAR) [21, 22, 25, 41].
- Implémenter une gestion d'erreur spécifique pour le message : `"Time to confirm expired"` en déclenchant automatiquement le flux de refresh [41-44].
Ce qui a été ajouté pour être "sûr à 100%" :
• Le flux de rafraîchissement automatique : Les sources précisent bien qu'au-delà de 30 secondes, le taux expire. J'ai ajouté une règle pour que l'IA prévoie ce cas d'erreur.
• La précision sur le "Memo" : Pour certains réseaux (comme TON ou Stellar mentionnés dans les exemples), le champ memo est indispensable bien que marqué comme optionnel dans l'absolu.
• Détails de la Travel Rule : J'ai spécifié les valeurs exactes ("individual"/"entity") pour éviter que l'IA n'invente des termes.
• Structure de l'objet Currency : Les sources montrent que les devises ont des propriétés comme is_fiat, is_stable et precision, ce qui est crucial pour formater les montants correctement avant l'envoi.
